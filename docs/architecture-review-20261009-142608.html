Code trace: signed-in caller supplies another owner's entry → fork is created → fork is recorded for caller → parent permission fails → HTTP 403. The rejection happens after the writes. This is an inspected call order; no live account probe was run.
Problem
The interface lets callers change a conversation before they check ownership.
Solution
Deepen the existing conversation module so ownership, entry resolution, and mutations stay together; keep HTTP formatting in its adapter.
Why depth
The caller no longer needs to know when permission must be checked; the implementation owns that rule at one seam.
Deletion test
Delete this responsibility and each caller must coordinate ownership, harness writes, and application records again.
  • Locality: one ownership decision
  • Leverage: all conversation callers
  • Tests cross the same interface
Test surface and scope
  • No first-party Gateway test file was found under src/. Add caller-level cases for allowed, missing, and foreign-owned entries; a rejected fork must leave both stores unchanged.
  • Use isolated storage adapters for tests. Keep the existing Drizzle and harness implementation; do not add a generic repository module.
  • This does not make the two stores atomic. Crash recovery is a separate decision, not a claimed benefit of this refactor.

Code trace: server returns slow_down → diagnostic text changes → next delay uses the same fixed pollInterval. Also, Cancel resets visible state but does not cancel the launched attempt.
Problem
The auth interface exposes challenge details and string diagnostics, so callers must understand the protocol.
Solution
Deepen the existing auth module to own each attempt from challenge to completion or cancellation; leave browser actions with the UI adapter.
Why depth
One seam contains timing and terminal outcomes; ViewModels do not handle credentials or infer protocol state from counters.
Deletion test
Delete the auth module and polling, expiry, revocation, and credential settlement move into its callers.
  • Locality: attempt policy stays together
  • Leverage: simpler sign-in caller
  • Existing fake adapter remains useful
Test surface and scope
  • SignInViewModelTest.kt:26–53,94–102 uses a fake auth adapter that returns success; it does not test real polling.
  • Test pending → slow-down timing, denied, expired, invalid grant, cancellation, and one browser handoff through the auth interface with controlled transport and time.
  • Keep one :app module, Navigation 3, lifecycle-aware state, direct Keystore encryption, and Context-free ViewModels.
  • Do not replace the chosen device authorization flow. These changes correct its implementation.

Code trace: history contains “Again” → user sends “Again” → unchanged history snapshot arrives → content match removes the new pending row. The generated key is not sent to the Gateway. A separate HTTP failure also leaves the page draft cleared.
Problem
The projection tests do not cover the implementation that joins pending delivery, HTTP results, snapshots, and draft recovery.
Solution
Concentrate delivery policy in the existing chat responsibility and let React own presentation; retain the useful projection module.
Why depth
Callers and tests cross one chat seam instead of coordinating independent pending, stream, and draft interpretations.
Deletion test
Delete chat delivery and each caller must reconcile HTTP and snapshots; deleting the projection alone would only relocate useful implementation.
  • Locality: delivery rules stay together
  • Leverage: page and suggestion callers
  • Tests cover HTTP and SSE order
Test surface and scope
  • The three existing web tests cover projection, not delivery. Add repeated-text, HTTP-before-SSE, SSE-before-HTTP, rejected-send, and edited-draft recovery cases.
  • Android already guards repeated text using known entry IDs; reuse the behavioral fixture cases, not Kotlin implementation in TypeScript.
  • Keep browser and Android transport adapters separate. Shared fixtures provide leverage without a cross-language runtime module.
  • No automatic message replay. Stable request identity needs Gateway support; do not claim exactly-once delivery from a local key.
