Attention asks for your decision.
Tasks shows the work behind it.

One chat can produce many engine tasks. An approval is a decision about one action—not a second chat message, and not a saved todo.

1. Three things with different jobs

Attention: “What needs me?”

A user-facing collection of signals from your conversations.

  • Pending approvals: decide whether an action may proceed.
  • Due or delivered reminders: see what was scheduled.
  • Failed tasks: investigate work that could not finish.
  • Delivered subagent reports: read delegated results.

It does not contain every tool call or every finished model request. It is a view of existing records, not a separate worker queue. Items have a link to their source chat.

Tasks: “What is the agent doing?”

Pi Durable's persisted execution records: the steps needed to do the work.

  • Assistant responses: model generation and orchestration.
  • Tool actions: save a todo, clear todos, send a digest.
  • Approval decisions: keep a tool paused until you decide.
  • Conversation summaries, reminder tasks and subagent reporters.

Includes completed steps as well as live work. A reminder can be a Task now, then an Attention item when it becomes due.

Saved todos: “What do I need to do?”

“Review an application” is a domain record in app SQL's todos table. It is not a Pi engine task. The save_todo engine task creates that record; clear_todos changes its status after approval.

2. Why Tasks looked like only a number

The integer was a task ID. Pi assigns each execution record an identity. It was not “you have 12 tasks,” a todo title, or an intentional privacy placeholder.

What the API actually returns

{
  id: 12,
  kind: "pi.tool",
  conversationId: 2,
  state: { status: "running", ... }
}
Illustrative IDs; the field names are Pi's real contract.

What the old UI tried to read

task.name      // absent → blank heading
task.status    // absent → blank badge
task.id        // present → ID: 12

The UI now reads kind and state.status. It shows a friendly title, status, ID and source link.

Details are not all hidden. “Execution details” reveals kind and conversation ID. Raw checkpoints are internal replay state—not a useful user description—and may contain tool arguments or provider data. The chat is where you read the requested action, decision, tool result and answer.

3. The old approval flow stopped twice

Break A: “blocked” was not “paused”

model requests clear_todos
  beforeTool creates SQL approval
  beforeTool returns { block: ... }
  Pi settles the tool as blocked
  agent receives a tool error and finishes

There was no suspended tool left for your approval to resume. “Waiting for your decision” could be model prose rather than actual runtime state.

Break B: the decision stayed in SQL

Attention → POST /approvals/:id/approve
  UPDATE approvals SET status = 'approved'
  return { success: true }
  STOP

No waiting task consumed that decision. No new transcript entry was written. SSE could not display an event that never existed.

Restart had a third gap

Harness.open() loads storage, but scheduling is enabled separately. Startup now calls harness.resume() so persisted work can continue without a browser submitting another message.

4. Walk the fixed flow

Interactive teaching diagram only. It makes no API calls and changes no real todos. Advance through the actual code's boundaries.

1 · TOOLRequest and pause
2 · HTTPAttention decides
3 · APP SQLSave the decision
4 · PI STORAGEFinish the approval wait
5 · TOOL + MODELContinue the same run
6 · SSE → UIShow the updates

No second user message. The original clear_todos tool awaits its own approval task with api.waitForTask(). The model continues after receiving that tool's result.

The approval task checks its one SQL decision every 250 ms using Pi's cancellation-aware sleep. This is server-side, only while an approval is pending—not browser polling. It avoids a fragile second “delivered” flag across two databases. Network/query time is additional; it is automatic, not an instantaneous push signal.

5. What survives a closed tab or restart?

App database

  • user_conversations: ownership and chat titles.
  • approvals: who requested what and whether you approved, rejected, or consumed permission.
  • todos: the actual pending/completed items.

For approval, the API checks user ownership and updates only pending rows. A competing second decision gets HTTP 409.

Pi Durable database

  • Original generation and tool execution records.
  • A memo that binds this tool to one proposal.
  • A tool-scoped document holding the owned approval-task ID.
  • Persisted lali.approval request and decision entries.
  • Model/tool entries and live conversation state.

Recovery rejoins the same approval task. It does not ask for a new permission or rerun the original model request.

approved → consume permission + change todos in one app SQL transaction
rejected → do not change todos; return rejection to the model
cancelled → mark the request interrupted; remove it from Attention
restart  → resume persisted tasks; reread the saved decision
SSE      → observe committed chat state; never drive the agent

If the chat is closed, the server still runs and saves the answer. When opened later, its initial SSE snapshot contains the history. If already open, subsequent SSE frames update the same transcript and approval card.

Previously-created requests whose old tool already settled are not suspended executions. The new pause/resume contract applies to requests created by the fixed tool; a completed old run cannot be retroactively turned into a paused one.
